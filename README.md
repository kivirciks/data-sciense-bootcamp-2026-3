# data_science_bootcamp_2026_avito_bot_detection

## 1. Постановка задачи

**Цель:** разработать модель машинного обучения для определения вероятности того, что трафик, связанный с `cookie_id`, является автоматизированным (bot), а не человеческим.

**Область применения:** обнаружение автоматизированного scraping / data collection traffic и ранжирование cookie по степени вероятности того, что они относятся к бот-трафику.

**Тип задачи:** бинарная классификация с последующим ранжированием.

**Единица наблюдения:** `cookie_id` с соответствующим 24-часовым окном наблюдения.

**Целевая переменная:**
- `target = 1` - cookie относится к известному автоматизированному трафику;
- `target = 0` - cookie относится к трафику, размеченному как человеческий.

**Предсказание:** для каждого `cookie_id` необходимо получить `score` в диапазоне `[0, 1]`, где большее значение означает большую вероятность bot-трафика.

**Основная метрика оценки:** `Precision @ Recall >= 0.70`.

Метрика выбирает максимальное значение precision среди всех порогов, при которых recall не меньше 70%.

Важная особенность метрики - cookie с одинаковым `score` рассматриваются как одна группа и не могут быть разделены между положительным и отрицательным классом.

## 3. Методология решения

### 3.1. Контроль качества данных

Перед построением признаков выполняются проверки:

1. `cookie_id` уникален в `train.csv`;
2. `cookie_id` уникален в `test.csv`;
3. cookie из train и test не пересекаются;
4. `target` принимает только значения `0` и `1`;
5. `window_end_ts > window_start_ts`;
6. продолжительность окна составляет 24 часа;
7. проверяются полные дубликаты событий;
8. проверяются потенциальные дубликаты по `cookie_id + event_ts + eid`.

Дополнительно проверяется корректность временной фильтрации событий.

---

### 3.2. Фильтрация событий

Ключевым требованием задачи является использование только событий, попадающих в индивидуальное окно соответствующего cookie.

Для каждого события используются границы:

```text
window_start_ts
window_end_ts
```

и применяется условие:

```text
window_start_ts <= event_ts < window_end_ts
```

Таким образом:

- события до начала окна не используются;
- события после окончания окна не используются;
- событие с `event_ts == window_end_ts` не относится к данному окну.

Это позволяет избежать temporal leakage и строго соблюдать постановку задачи.

---

### 3.3. Создание признаков

Для train и test используется единая функция feature engineering:

```python
build_features(events_df)
```

Признаки строятся на уровне `cookie_id`.

#### Активность

- `n_events` - количество событий;
- `median_gap_sec` - медианный интервал между событиями;
- `n_unique_eids` - количество уникальных событий;
- `n_unique_items` - количество уникальных товаров.

#### User-Agent

- `ua_n_unique` - количество уникальных User-Agent;
- `ua_is_headless_any` - наличие headless browser;
- `ua_is_headless_share` - доля событий с headless browser;
- `ua_is_bot_lib_any` - наличие признаков bot library;
- `ua_is_bot_lib_share` - доля событий с bot library.

#### Поведенческие признаки

- `captcha_share` - доля captcha-событий;
- `engagement_share` - доля engagement-событий;
- `query_uniqueness` - уникальность поисковых запросов;
- `max_search_page` - максимальная страница поиска;
- `mean_search_page` - средняя страница поиска.

#### Pointer-события

Используются обе координаты:

- `pointer_x_unique_ratio`;
- `pointer_y_unique_ratio`;
- `pointer_xy_unique_ratio`;
- `pointer_zero_zero_share`.

#### Дополнительные признаки

- `cookie_age_h` - возраст cookie в часах;
- `top_platform` - наиболее часто встречающаяся platform.

---

### 3.4. Почему используются поведенческие признаки

Автоматизированный трафик может отличаться от человеческого по совокупности характеристик:

- частоте событий;
- регулярности интервалов;
- структуре поисковых действий;
- поведению pointer-событий;
- использованию headless browser;
- User-Agent;
- взаимодействию с captcha;
- характеру engagement;
- повторяемости действий.

Поэтому модель использует комбинацию поведенческих сигналов вместо одного правила классификации.

---

### 3.5. Предобработка данных

Для числовых признаков используется:

```text
Median Imputation
        ↓
StandardScaler
```

Для категориальных признаков:

```text
Most Frequent Imputation
        ↓
OneHotEncoder
```

Предобработка реализована внутри sklearn `Pipeline` / `ColumnTransformer`.

Это позволяет выполнять все операции отдельно внутри каждого training fold и предотвращает утечку статистик validation-части в обучение.

## 4. Валидация

### 4.1. Временная структура данных

Тестовая выборка находится позже во времени относительно train.

Поэтому случайное перемешивание наблюдений не используется как основная схема валидации.

Случайный `StratifiedKFold` может смешивать прошлые и будущие периоды и давать оценку, которая хуже отражает реальный сценарий применения модели.

---

### 4.2. Expanding Window Validation

Используется временная cross-validation по дням.

Для каждого validation fold:

```text
прошлые дни → следующий день
```

Например:

```text
Fold 1:
Day 1 ... Day N     → Day N+1

Fold 2:
Day 1 ... Day N+1   → Day N+2

Fold 3:
Day 1 ... Day N+2   → Day N+3

Fold 4:
Day 1 ... Day N+3   → Day N+4
```

Таким образом, validation всегда находится в будущем относительно training data.

Такая схема имитирует реальный процесс:

```text
исторические данные
        ↓
обучение модели
        ↓
будущий период
        ↓
предсказания
```

---

### 4.3. OOF predictions

Для каждого кандидата формируются out-of-fold predictions.

При expanding-window validation первые дни могут использоваться только в качестве training data и не иметь OOF-предсказаний.

Поэтому исходный OOF-массив может содержать `NaN`.

При расчёте метрик используются только строки с фактическим OOF prediction.

Это позволяет одновременно:

- сохранить корректную временную схему;
- не использовать данные будущего;
- корректно рассчитывать метрики.

## 5. Модели

В эксперименте рассматриваются следующие алгоритмы:

- Logistic Regression;
- Gradient Boosting;
- Random Forest;
- LightGBM;
- XGBoost.

Для моделей подбираются основные гиперпараметры, включая:

- `C`;
- `class_weight`;
- `n_estimators`;
- `max_depth`;
- `learning_rate`;
- `min_samples_leaf`;
- `scale_pos_weight`.

Подбор параметров выполняется через `GridSearchCV` с временной cross-validation.

В качестве surrogate-критерия при поиске гиперпараметров используется `Average Precision`.

После подбора параметров модели сравниваются непосредственно по основной метрике кейса:

```text
Precision @ Recall >= 0.70
```

---

## 6. Официальная метрика

Для оценки используется предоставленный организаторами `metric.py`.

Основная метрика:

```text
Precision @ Recall >= 0.70
```

Алгоритм расчёта:

1. cookie сортируются по `score` по убыванию;
2. одинаковые значения `score` объединяются в одну группу;
3. для каждой группы рассматривается соответствующий threshold;
4. рассчитываются precision и recall;
5. выбирается максимальный precision среди порогов, где:

```text
Recall >= 0.70
```

Это важно, поскольку precision по мере снижения threshold не обязательно монотонно уменьшается.

Также реализована диагностическая метрика:

```text
Recall @ FPR <= 1%
```

Она используется для дополнительного анализа качества модели и не является основной метрикой соревнования.

---

## 7. Результаты

### 7.1. Сравнение моделей

Финальное сравнение моделей выполняется на out-of-fold предсказаниях временной валидации.

Для каждой модели рассчитываются:

| Метрика | Назначение |
|---------|------------|
| ROC-AUC | Общая способность модели разделять классы |
| PR-AUC / Average Precision | Качество ранжирования положительного класса |
| Precision @ Recall >= 0.70 | Основная метрика кейса |
| Recall @ FPR <= 1% | Дополнительная диагностика |

Конкретные значения метрик зависят от фактического запуска ноутбука на исходных данных.

---

### 7.2. Выбор модели

Финальная модель выбирается по:

```text
Precision @ Recall >= 0.70
```

Дополнительно анализируются результаты отдельных временных folds, чтобы оценить стабильность качества во времени.

Таким образом, выбор модели не основывается только на одном случайном train/validation split.

---

## 8. Финальное обучение

После выбора модели она переобучается на полном объёме обучающих данных.

Затем для каждого `cookie_id` из `test.csv` рассчитывается:

```text
score ∈ [0, 1]
```

Формируется файл:

```text
submission.csv
```

с двумя колонками:

```text
cookie_id
score
```

Перед сохранением выполняются проверки:

- количество строк совпадает с `test.csv`;
- `cookie_id` уникальны;
- порядок `cookie_id` совпадает с test;
- отсутствуют пропущенные значения;
- все `score` находятся в диапазоне `[0, 1]`.

## 9. Основные выводы

### 9.1. Корректная временная фильтрация является критичной

При построении признаков недостаточно просто объединить `events` с train/test по `cookie_id`.

Необходимо учитывать индивидуальное окно:

```text
window_start_ts <= event_ts < window_end_ts
```

Иначе в признаки может попасть информация, которая не должна быть доступна модели.

---

### 9.2. Временная валидация лучше соответствует задаче

Поскольку test расположен позже train, основная схема валидации должна сохранять направление времени:

```text
past → future
```

Это позволяет получить более реалистичную оценку поведения модели на будущих данных.

---

### 9.3. Основная метрика должна использоваться при финальном сравнении

ROC-AUC и PR-AUC являются полезными диагностическими метриками, но непосредственно задача оценивается по:

```text
Precision @ Recall >= 0.70
```

Поэтому именно эта метрика используется для окончательного сравнения кандидатов.

---

### 9.4. Одинаковые score нельзя разделять

Официальная метрика рассматривает одинаковые значения `score` одной группой.

Следовательно, реализация локальной метрики должна полностью соответствовать `metric.py`, иначе локальная оценка может отличаться от оценки проверяющей системы.

---

### 9.5. Комбинация поведенческих признаков

Для определения bot-трафика используются несколько групп сигналов одновременно:

- активность;
- интервалы между событиями;
- User-Agent;
- headless browser;
- bot libraries;
- поисковое поведение;
- captcha;
- engagement;
- pointer events.

Такой подход позволяет модели учитывать различные проявления автоматизированного поведения.
